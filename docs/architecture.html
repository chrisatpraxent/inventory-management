Architecture Reference

Factory Inventory Management System

A two-process demo application: a Vue 3 single-page app talks to a Python FastAPI service over HTTP/JSON. There is no database — the API loads seven JSON files into memory at import time and filters them in Python on every request.

System architecture

Two independent processes, started separately, communicating only over HTTP on the developer's machine. Because they sit on different ports, every API call is cross-origin, which is why the backend enables permissive CORS.

Data flow: one filter change

The four global filters are the spine of the application. They live in one module-level singleton, so changing a filter in the header re-drives whichever view is currently mounted. This is the path a single interaction takes end to end.

Two asymmetries worth knowing

  • Inventory has no time dimension. /api/inventory accepts only warehouse and category, so the Time Period and Order Status filters silently do nothing on inventory-driven numbers. Six of the thirteen routes ignore filters entirely.
  • /api/dashboard/summary is partly unfiltered. It applies the filters to inventory and orders, but total_backlog_items is computed from the full global backlog list — that tile does not move when filters change.

Data layer

mock_data.py reads every file once at import and binds each to a module-level name. There is no reload, no write path, and no cache invalidation — editing a JSON file requires a server restart to take effect.

Because orders.json stores warehouse and category on the order itself rather than resolving them through line-item SKUs, order filtering never has to join against inventory — that redundancy is what makes single-pass list filtering viable.

Where client and server disagree

The most important thing to know before adding a feature: api.js has grown past the API. Six of its seventeen methods call routes that main.py does not define. Verified against the running server — all six return 404.

Client methods with no server route

  • GET /api/tasks, POST /api/tasks, DELETE /api/tasks/{id}, PATCH /api/tasks/{id} — called by App.vue for the tasks modal
  • POST /api/purchase-orders, GET /api/purchase-orders/{backlogItemId}

App.vue merges currentUser.tasks (hardcoded in useAuth) with apiTasks from the failing fetch, so the modal still shows the four mock tasks and the failure is invisible in the UI. Adding these six routes to main.py would make the existing frontend work as written.

Running and testing

Two processes, started separately

  • Backend — cd server && uv run python main.py, binds 0.0.0.0:8001
  • Frontend — cd client && npm run dev, port pinned to 3000
  • OpenAPI docs — localhost:8001/docs, generated from the Pydantic models
  • Order matters only for data: the SPA renders with empty states if the API is down

Test suite — 40 tests

  • test_misc_endpoints.py — 17
  • test_dashboard.py — 13
  • test_inventory.py — 10
  • conftest.py injects server/ onto sys.path and yields a TestClient, so tests run in-process with no live server
  • Run with cd tests && uv run pytest backend/ -v

Demo-only security posture

CORS allows every origin with credentials enabled; there is no authentication, authorisation, rate limiting, or input sanitisation beyond Pydantic type coercion. useAuth hardcodes isAuthenticated = true. The service binds 0.0.0.0, so it is reachable from the local network. Appropriate for a local demo, not for deployment.
